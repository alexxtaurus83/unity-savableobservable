# Reusable Strict MMVC Guard for Kilo

## Goal and Decisions

Create a reusable Kilo plugin that supplies MMVC guidance, requires the MMVC skill before C# edits, and rejects confidently detected new framework violations. Distribute it from this repository and install it alongside AttaxUnity's existing guard.

- User selected strict enforcement, a separate reusable plugin, and blocking only newly introduced violations.
- User accepted the detection limitations and explicitly requires checking files created from scratch, keeping the canonical plugin in a new local folder, deploying it to AttaxUnity, and including Markdown usage/client/rationale documentation.
- Keep `F:\Unity_projects\AttaxUnity\.kilo\plugin\attax-guard.ts` unchanged. Its context, planning, and search gates remain independent.
- Do not promise that a plugin prevents every agent mistake. This is workflow enforcement and conservative linting, not a security sandbox or a replacement for compilation, review, and Unity tests.
- Out of scope: framework runtime changes, bulk cleanup, a Roslyn analyzer, scene/prefab mutation, package installation in Unity, npm publishing, and policing arbitrary shell programs or external editors.

## Implementation

### Activation and Guidance

1. Activate when the project `Packages/manifest.json` declares `com.evialdev.savableobservable`; support embedded/local resolution without editing package sources. Otherwise stay inert. Allow an explicit project opt-in for unusual manifest layouts.
2. Default `MMVC_GUARD_MODE` to `enforce`; support explicit `warn` and `off` modes. Never disable enforcement automatically after a failure. State that environment/configuration controls are an operator escape hatch, not a security boundary.
3. Resolve skill files from an explicit configured directory, project `.kilo/skills/mmvc-unity`, then the installed user skill directory. Resolve the home directory portably rather than hardcoding this machine's username. Report missing or malformed skills with actionable paths.
4. Use `experimental.chat.system.transform` to append a short MMVC checklist and an instruction to load `mmvc-unity`. Cover smallest meaningful component shape, Logic -> Model -> Presenter flow, same-object binding, initialization, tracked subscriptions, persistence, and two-Play-run verification where relevant.
5. Use `experimental.session.compacting` to preserve those requirements without replacing Kilo's compaction prompt. Never inject guidance into user messages or repeatedly append full reference files.

### Successful Skill-Load Gate

1. Track successful skill loads per session through `tool.execute.after`, not mere attempts in `before`. Recognize the actual `skill { name: 'mmvc-unity' }` tool and successful direct `read` of the resolved `SKILL.md` as the fallback. A path mentioned in a prompt does not count.
2. Inspect the real Kilo success/error metadata and read response behavior before implementing success classification. Failed, empty, or truncated reads must not silently satisfy the gate.
3. Require the gate before supported C# mutations under the active project, including new files and deletions. Exclude generated `Library`, `Temp`, and `obj` paths from application linting; reject edits to cached framework package source rather than suggesting them as fixes.
4. Treat child sessions independently: parent skill loading does not prove the child received skill content. Requiring a load in the child avoids that false assumption. Restarted plugin state requires reloading; compaction retains the gate plus the compact reminder.
5. Return a clear rejection naming `skill` and the direct-read fallback. Missing references do not trigger unrelated C# writes; load task-relevant references as instructed by the skill.

### Mutation Inspection

1. Support the actual Kilo argument schemas for `write`, `edit`, `multiedit`, and `apply_patch`/`patch` where exposed. Read pre-edit content and reconstruct proposed content in memory, including multi-file patches, rename destinations, additions, deletions, relative/absolute paths, and Windows separators.
2. Canonicalize paths against the project root. Do not inspect unrelated external projects. A rename into project scope is an addition; preserve old/new path identity for diagnostics.
3. Validate every affected file before allowing any part of a multi-file operation. Do not mutate files from the guard, partially apply a patch, or attempt rollback.
4. If a recognized in-scope C# mutation cannot be reconstructed unambiguously, reject it with an instruction to use a supported edit form. Do not silently skip it. Tool-schema uncertainty must be resolved with fixtures and the installed client, not guessed.
5. Compare pre/post diagnostics using stable rule/type/member identities and occurrence counts, not line numbers. Existing violations may remain or be removed; newly introduced occurrences are blocked. Report original violations as bounded warnings only. New files have no baseline.
6. For a C# file created from scratch through `write` to a nonexistent path or patch `Add File`, lint the entire proposed file against an empty baseline and require successful skill loading before creation. Every detected blocking violation is new; creation must never bypass the checks merely because no original file exists. Apply the same rule to copies/renames entering scope through supported mutation tools.

### Initial Rule Set

Use a lightweight lexical scanner that masks comments and all C# string/character literal forms while preserving positions, balances declaration/member scopes, and recognizes direct framework inheritance. Do not infer types from class-name suffixes. Ambiguous or unresolved type relationships produce review warnings, not invented certainty.

Block new occurrences of these conservative, syntactically provable cases:

- An application class directly declaring `ISharedSingleton` while directly deriving from a known framework model or presenter base.
- `Services.Get<T>()` where `T` resolves within the inspected source to a known model or presenter type; recommend Logic access or `Services.GetModel<M>()` as applicable.
- Inside a known Logic class, explicit typed presenter fields, presenter construction, or presenter component lookups whose types are known in the inspected source. Exempt the required presenter type argument in `BaseLogic<M, P>` and do not block unrelated Editor tooling.
- An unambiguous override of `InitializePresenter()` with no `base.InitializePresenter()` invocation; warn rather than claiming full control-flow verification when the call exists conditionally or late.

Do not hard-block uncertain rules using broad regexes. Warnings/review guidance cover external/custom inherited types, aliased presenter access, direct calls with unresolved receiver types, dummy components, UI setup in `Start`, required `[NonSaved]` intent, manual subscription teardown, initial rendering, raw list mutations without a proven observable receiver, and same-GameObject/service-locator scene state. Document the limited initial rule set explicitly.

Each diagnostic includes a stable rule ID, path, line, reason, and valid replacement pattern. Model-to-view one-shot commands should point to the skill's observable event-token pattern. Do not automatically rewrite user code.

## Validation

1. Run isolated typecheck and unit tests against `@kilocode/plugin@7.4.5`; record actual commands/results. Avoid installing anything into the Unity root package.
2. Test inactive projects; missing skills; successful/failed skill calls and direct reads; independent child sessions; compaction reminders; enforce/warn/off modes; and restarting state.
3. Test every supported mutation form, multi-file all-or-nothing rejection, new/deleted/renamed files, CRLF, Windows and relative paths, malformed/ambiguous edits, excluded paths, and cache protection.
4. Test each rule with positive and negative C# fixtures, including comments, ordinary/verbatim/interpolated/raw strings, required presenter generic arguments, plain services, model-only state services, custom inheritance, and unrelated classes with Presenter-like names.
5. Prove unchanged baseline violations and line shifts do not block; adding another occurrence does block; fixing one violation while introducing a different one still blocks.
   Explicitly test clean and violating new C# files through both `write` and patch `Add File`, creation before/after skill loading, and a mixed multi-file patch containing a violating new file. Assert rejection occurs before any fixture file is created or edited.
6. In a fresh disposable Unity-project fixture, smoke-test real Kilo plugin discovery, system injection, skill load, blocked/allowed edits, and coexistence with the existing Attax guard. Do not modify gameplay files merely to demonstrate rejection.
7. Deploy only after those tests pass. Reload/restart Kilo using the installed client's verified mechanism and confirm both plugin IDs load without duplicate-export errors. If live-client validation is unavailable, report that gap explicitly rather than calling it verified.
   Verify the deployed `F:\Unity_projects\AttaxUnity\.kilo\plugin\mmvc-guard.ts` is byte-identical to the canonical `mmvc-kilo-plugin/mmvc-guard.ts`, and that the existing Attax guard remains unchanged. The README must describe repeating this copy-and-verify process for updates.
8. No Unity runtime behavior changes are intended, so Unity builds and Play Mode runs are not required solely for this plugin. The plugin must continue to instruct agents to run relevant Unity verification for future gameplay changes.

## Rollout and Failure Handling

- Rollback consists of removing only the deployed `mmvc-guard.ts` and reverting only this task's enforcement documentation changes, then reloading Kilo. Do not modify or disable `attax-guard.ts`.
- Preserve any pre-existing worktree changes. Do not commit, publish, or modify the installed shared skill without explicit authorization.
- If SDK hook behavior or tool metadata differs from its declarations, resolve it in the fixture first. Report any unsupported client boundary honestly.
- Completion report lists rule coverage, actual checks run, deployment state, and residual bypass/semantic limits. Never claim the agent can no longer make mistakes.
